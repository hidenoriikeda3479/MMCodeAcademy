# 勉強会のおさらい：設計書から作るTODOアプリ

## 今日のゴール

設計書を見ながら、TODOアプリの**担当者の新規登録**を作り進める。今回は作成中のコードを確認し、入力チェック、更新の競合、コードの整理方法を学んだ。

**現在地：** データベースの項目の消し忘れによるマイグレーションの問題は修正でき、アプリは起動できる。新規登録は作成中で、更新・削除はまだ完成していない。

## 実現したい動き

### 新規登録

1. 入力内容を設計書の条件に照らしてチェックする。
2. 問題がなければデータベースに保存する。
3. 成功・失敗に応じたメッセージを表示する。

入力だけで判断できるエラーは、データベースへ接続する前に知らせる。

### 更新

編集画面を開いたときの**対象データの更新日時**を覚えておく。保存する直前に更新日時をもう一度取得し、値が変わっていたら保存しない。これが今回扱う**楽観的排他制御**。更新処理自体は、これから実装する。

| 方法 | ほかの人との競合への対応 |
| --- | --- |
| 楽観的排他制御 | 保存直前に更新日時を比較し、違っていたら保存しない。今回使う方法。 |
| 悲観的排他制御 | 編集を始める段階から、ほかの人が同じデータを扱えないようにする。授業では比較として学んだ方法。 |

## 考え方

### 設計書を出発点にする

項目、入力条件、メッセージを設計書で確かめる。空白を取り除く `Trim` は設計書にない処理だったが、今回の課題では使ってよいと確認された。判断に迷う点は質問する。

### 一つのメソッドに詰め込まない

保存ボタンの処理から**入力チェック**と**登録**を分ける。授業では、チェック結果を `true` / `false` で返す方法も示された。役割ごとに分けると、処理の流れを追いやすい。

### 固定の値をまとめる

エラーメッセージ、確認メッセージ、意味を持つ数値は、用途に合わせて定数クラスにまとめる。メッセージIDが設計書にあれば、名前を決める参考にする。

| 用語 | 今回の要点 |
| --- | --- |
| `const` | 定義するときに値を決め、その後は変えない定数。 |
| `readonly` | コンストラクターで値を設定でき、その後は変更しない。 |
| `static` | クラスのメンバーを、`new` でインスタンスを作らずに使える。`static` 自体は「値が変わらない」という意味ではない。 |
| `partial` | 画面のコードとデザイナー側のコードのように、別ファイルに分かれた同じクラスを一つとして扱う。 |

## 注意点

- 未入力チェックは、文字数が `0` かを調べる代わりに `string.IsNullOrEmpty` を使うよう助言があった。
- データベースの項目を消し忘れたままマイグレーションすると、起動や保存でエラーになることがある。今回の問題は修正済み。
- クラスとイベントには、何をする処理か分かるコメントを付ける。レビュー前に空行やコードの配置も整える。

## 確認問題

1. 新規登録では、どの処理をデータベース接続より先に行いますか。
2. 楽観的排他制御で比べる二つの日時は何ですか。違っていたらどうしますか。
3. `const`、`readonly`、`static` は、それぞれ何が違いますか。
4. 保存ボタンの処理を、どの二つの役割に分けますか。

## 次回までの課題

1. 新規登録の未完成部分を進め、入力チェックを別メソッドに分ける。
2. メッセージや意味を持つ数値を定数として整理し、未入力チェックに `string.IsNullOrEmpty` を使う。クラスとイベントのコメントも付ける。
3. 設計書を確認しながら更新・削除の作業を進め、分からない点は質問する。次回扱うオブジェクト指向の**継承**について調べておく。
